# Integration with `~/raja/oc` (the SuryaOS agent)

How to deploy `functiongemma:270m-suryaos` after training and feed real
failures back into the dataset.

---

## Architecture

```
┌─────────────────────────────────────────────────────────┐
│  ~/raja/functiongemma-suryaos     (this repo)           │
│  ─────────────────────────────                          │
│  Train → Export → Push to Ollama                        │
│                                                          │
│  output: ollama/functiongemma:270m-suryaos              │
└──────────────────────────┬──────────────────────────────┘
                           │
                           │ ollama push (or ollama create locally)
                           ▼
┌─────────────────────────────────────────────────────────┐
│  Ollama daemon (this machine)                           │
│  ─────────────────────────────                          │
│  registry.ollama.ai/library/functiongemma:270m-suryaos  │
└──────────────────────────┬──────────────────────────────┘
                           │
                           │ inference at :11434
                           ▼
┌─────────────────────────────────────────────────────────┐
│  ~/raja/oc                       (the agent runtime)    │
│  ─────────────────────────────                          │
│  opencode.json: coder-fg agent → ollama/functiongemma   │
│  mcp/system.py + mcp/volume.py: 11 MCP tools            │
│  src/surya_agent/context_builder.py: FTS+graph→prompt   │
│  runtime/audit.db: every dispatch logged                │
└──────────────────────────┬──────────────────────────────┘
                           │
                           │ failures captured
                           ▼
┌─────────────────────────────────────────────────────────┐
│  ~/raja/oc/tests/results/*_additions.jsonl              │
│  ─────────────────────────────                          │
│  bash scripts/test_and_collect.sh syncs back to:        │
│  ~/raja/functiongemma-suryaos/dataset/dispatch_pairs.jsonl│
└─────────────────────────────────────────────────────────┘
                           │
                           └──── retrain (loop)
```

## Step 1 — Deploy the trained model

After running `python3 training/finetune.py --mode all`:

```bash
# Modelfile is generated by --mode export
ollama create functiongemma:270m-suryaos -f training/output/Modelfile

# Verify
ollama list | grep suryaos
ollama show functiongemma:270m-suryaos
# Should print: capabilities: completion, tools
```

If you trained on a different machine (RTX 3080 box), copy the Modelfile
and the merged GGUF over:

```bash
# On RTX 3080 box, after training
scp training/output/* user@suryaos-laptop:~/raja/functiongemma-suryaos/training/output/

# Back on SuryaOS laptop
cd ~/raja/functiongemma-suryaos
ollama create functiongemma:270m-suryaos -f training/output/Modelfile
```

---

## Step 2 — Switch the coder-fg agent

In `~/raja/oc/opencode.json`, the `coder-fg` agent is reserved for the
fine-tuned functiongemma. Currently:

```json
"coder-fg": {
    "description": "RESERVED: functiongemma:270m post-finetune testing.",
    "model": "ollama/functiongemma:270m",     ← base model
    ...
}
```

Change to:

```json
"coder-fg": {
    "description": "Production: fine-tuned functiongemma for SuryaOS.",
    "model": "ollama/functiongemma:270m-suryaos",   ← your trained model
    ...
}
```

The agent already has all 11 built-in tools disabled and no MCP filesystem,
so functiongemma sees only the SuryaOS MCP tools (volume + system) — exactly
the setup the training data assumes.

---

## Step 3 — Promote `coder-fg` to default `coder` (when verified)

After confirming the fine-tuned model passes 80%+ at L3, swap the default
coder agent to use it:

```json
"coder": {
    "description": "All desktop tool calls. functiongemma:270m-suryaos.",
    "model": "ollama/functiongemma:270m-suryaos",   ← swapped
    "mode": "primary",
    ...
}
```

Now `opencode run --agent coder "..."` (or just plain `opencode run "..."`)
uses the fine-tuned model.

Keep the original `coder-fg` agent as a regression-test slot — set its
model back to `functiongemma:270m` (base) so you can A/B compare.

## Step 4 — Verify with the test harness

```bash
cd ~/raja/oc

# Quick smoke test (one query)
opencode run --agent coder "is bluetooth active"
# Expected: ⚙ system_service_status {"name":"bluetooth"}
#           bluetooth: active.

# Full L3 sweep — runs 200+ cases through opencode, captures failures
bash scripts/test_and_collect.sh --with-model
# This takes ~30 min (200 cases × ~10s each) and writes
# tests/results/<timestamp>_L3.txt with the pass/fail breakdown.
```

Expected results after fine-tune:

| Category | Before fine-tune | After fine-tune (target) |
|---|---|---|
| basic | ~50% (model refuses many) | 95%+ |
| multi_arg | ~30% (model misses step/path args) | 90%+ |
| service_alias | ~20% (model invents tool names) | 95%+ |
| browser/app launch | ~60% | 95%+ |
| user_green | ~40% (refusals on RAM/Bluetooth) | 95%+ |
| admin_yellow | n/a (tools not impl yet) | n/a |
| admin_red | ~70% (correctly refuses) | 95%+ |

## Step 5 — Capture real failures into the dataset

The test harness writes failures to `tests/results/<ts>_failures_L3.jsonl`
in dispatch_pairs format. Sync them back:

```bash
cd ~/raja/oc
bash scripts/test_and_collect.sh --with-model
# Auto-syncs the new failures to ~/raja/functiongemma-suryaos/dataset/dispatch_pairs.jsonl
# (deduplicates by query)

# Then push the updated dataset
cd ~/raja/functiongemma-suryaos
git add dataset/dispatch_pairs.jsonl
git commit -m "data: +N failures from oc test run"
git push origin main

# On the GPU machine:
git pull
python3 training/finetune.py --mode train
```

This is the steady-state retraining loop. Run it weekly.

## Continuous capture from production usage

The agent already logs every dispatch to `~/raja/oc/runtime/audit.db`. To
capture real user queries (not just test failures) as training signal:

```bash
# Extract recent ALLOW dispatches and add as positive training pairs
python3 scripts/training/generate.py --mode audit
# Reads runtime/audit.db rows where decision='allow'
# Reconstructs (query, tool, args) triples
# Appends to training/dispatch_pairs.jsonl
```

After a month of active SuryaOS use, the audit log typically contains
500-1000 unique queries. Combined with the synthetic 1564, the dataset
reaches ~2000+ examples — the v4 target.

## Reverting (if a fine-tune regresses)

If the fine-tuned model performs worse than the base (rare but possible
with bad training data):

```bash
# In opencode.json, swap back:
"coder": {"model": "ollama/functiongemma:270m"}

# Optional: remove the bad model from Ollama
ollama rm functiongemma:270m-suryaos

# Investigate via the failure log
ls -t ~/raja/oc/tests/results/*_failures_L3.jsonl | head -1
```

LoRA adapters are stored separately in `training/model_lora/`, so reverting
is just a matter of pointing opencode back at the base model. The training
data and test harness stay intact.

## Cron-style auto-retraining

For a fully automated loop on a dedicated training box:

```bash
# /etc/cron.weekly/retrain-suryaos
#!/bin/bash
cd /home/raja/functiongemma-suryaos
git pull origin main
python3 training/finetune.py --mode all
ollama create functiongemma:270m-suryaos -f training/output/Modelfile
ollama push registry.ollama.ai/raja/functiongemma-suryaos:latest

# On SuryaOS laptops:
# /etc/cron.weekly/pull-suryaos-model
ollama pull registry.ollama.ai/raja/functiongemma-suryaos:latest
```

This way the model improves with every week of usage without manual intervention.
